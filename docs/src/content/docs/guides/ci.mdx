---
title: Running Routy in CI
description: Use your request files as API tests in GitHub Actions and other CI systems.
---

The same `.routy` (and `.http`) files you click through in the app can run as API tests on every push.
`expect` checks decide whether the job passes.

## GitHub Actions

```yaml title=".github/workflows/api-tests.yml"
name: API tests

on: [push, pull_request]

jobs:
  api:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # Start the service under test here (docker compose, a binary, …)

      - name: Install routy
        run: |
          curl -fsSL https://raw.githubusercontent.com/1rowvy/routy/master/install.sh | sh
          echo "$HOME/.local/bin" >> "$GITHUB_PATH"

      - name: Check request files
        run: |
          routy fmt --check api
          routy check api --env ci --no-keyring

      - name: Run API tests
        run: routy run api --env ci --no-keyring --fail-fast
        env:
          ROUTY_TOKEN: ${{ secrets.API_TOKEN }}
```

- Pin a version for reproducible builds: `ROUTY_VERSION=v0.2.0` before `sh`.
- Secrets come from `ROUTY_<NAME>` variables — see [Secrets](/routy/guides/secrets/#in-ci-environment-variables).
- `--no-keyring` skips the keychain lookup, which does not exist on runners anyway.
- The update notice is disabled automatically when the `CI` variable is set.

## Machine-readable output

`--json` prints one JSON object per request (JSON Lines) instead of the human-readable report:

```sh
routy run api --json > results.jsonl
```

```json
{"file":"api/users/get.routy","name":"GetUser","passed":true,"outcome":{"kind":"request","request":{…},"response":{"status":200,…},"asserts":[…],"calls":[…],"saved":{}}}
{"file":"api/users/bad.routy","name":"GetUser","passed":false,"error":"undefined variable(s): id"}
```

A flow's `outcome` has `"kind":"flow"` with `checks`, `calls`, `saved` and `error`.

## Lint without sending

`routy check` reads every file without sending requests — a fast lint step. In `.routy` it also checks
names of called requests, their arguments, shapes and call cycles. With `--env` it checks what depends
on the environment: requests whose `only` excludes it, and variables that are not defined in it:

```sh
routy check api
routy check api --env ci
```

```txt
api/orders/create.routy:7:22: variable `api_key` is not defined in ci
api/orders/create.routy:9:13: `Seed` is limited to dev and cannot be called in ci
```

`routy fmt --check api` fails when a file is not in the canonical style; `routy fmt api` fixes it.
