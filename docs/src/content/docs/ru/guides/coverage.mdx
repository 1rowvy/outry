title: Покрытие роутов

---

`outry coverage` отвечает на вопрос «какие ручки сервиса вообще ничем не проверены». Он читает роуты из
кода на Go или Rust (как [`outry import go`](/outry/ru/guides/import-go/) и
[`outry import rust`](/outry/ru/guides/import-rust/)), сопоставляет их с запросами проекта и
смотрит на их `expect`. Ничего не отправляется.

```sh
outry coverage
```

```txt
GET    /health       no request  codes 0/1  main.go:9
POST   /orders       no expect   codes 0/1  api/orders.outry:5  unchecked: 201
DELETE /orders/{id}  no expect   codes 0/1  api/orders.outry:9  unchecked: 204
GET    /orders/{id}  checked     codes 1/2  api/orders.outry:1  unchecked: 404

1/4 routes checked (25%): 2 without expect, 1 without request; 1/5 status codes checked
1 missing request can be created with `outry import go`
```

## Уровни

У каждого роута один из трёх уровней:

| Уровень | Что значит |
|---------|------------|
| `no request` | Роут есть в коде, но ни один запрос `.outry` или `.http` в него не ходит. `outry import go` его создаст. |
| `no expect` | Запрос есть, но его ответ ничто не проверяет. |
| `checked` | У запроса к роуту есть `expect` — свой или проверка его результата в другом месте. |

Запрос сопоставляется с роутом так же, как в `outry import go`: по `handler:`, а без него — по методу и
пути. Процент — доля роутов на уровне `checked`.

Запрос считается проверенным, если:

- у него самого есть `expect`;
- его результат проверяет другой запрос или сценарий: `expect { GetOrder(id: body.id).body.status == "new" }`;
- сценарий сохраняет его в переменную и проверяет её: `order = CreateOrder()` … `expect { order.status == 201 }`;
- в `.http` — есть строка `> assert`.

Запрос, который вызывается только ради значения (`Login()` в заголовке), проверкой `Login` не считается.

## Коды ответа

Outry ещё собирает коды, которыми отвечает каждый обработчик:

- константы `net/http` где угодно в обработчике: `http.Error(w, "…", http.StatusConflict)`,
  `c.JSON(http.StatusNotFound, …)` (те же имена у fiber и iris);
- числа от 100 до 599 в вызовах-ответах: `c.JSON(404, …)`, `w.WriteHeader(201)`, `c.AbortWithStatus(401)`,
  свой `respond(w, 409, …)`;
- обработчик без успешного кода отвечает `200` — такой код помечается как неявный.

Код проверен, если какой-то запрос к роуту сравнивает с ним статус:

```outry
GetOrder: GET /orders/{id} {
  expect { status == 200 }
}

flow MissingOrder {
  expect { GetOrder(id: 0).status == 404 }
}
```

Считаются `status == 404`, `404 == status` и `status in [200, 404]`; диапазоны (`status < 500`) проверяют
ответ, но конкретный код не отмечают. Коды, которые выставляют вспомогательные функции, вызываемые
обработчиком, не находятся.

## Выполненные роуты

Статическое покрытие говорит, что запрос есть и что-то проверяет, но не что он действительно выполнялся.
Журнал прогона показывает, какие роуты реально вызывались — сами, из другого запроса (`Login()` в
заголовке) или из сценария:

```sh
outry run api --coverage-out run.json
outry coverage --from run.json
```

```txt
POST   /login        no expect   ran      codes 0/1  api/orders.outry:1   via CreateOrder  unchecked: 200
POST   /orders       checked     ran      codes 1/1  api/orders.outry:5
DELETE /orders/{id}  no expect   not run  codes 0/1  api/orders.outry:15  unchecked: 204
GET    /orders/{id}  checked     ran      codes 2/2  api/orders.outry:10  via Missing

2/4 routes checked (50%): 2 without expect, 0 without request; 3/5 status codes checked; 3/4 routes executed (75%)
```

`--coverage-out` записывает каждый реально отправленный запрос: файл и имя, метод, URL, пришедший код
ответа, а для вызова — цепочку, из которой он вызван. Ответы из кеша прогона не отправляются и не
записываются. Запрос из журнала сопоставляется с роутом через запрос проекта (по файлу и имени, так что
правки после прогона не мешают; `.http` — по файлу), а если такого запроса уже нет — по методу и пути URL.
`via` показывает, что до роута дошли только косвенно.

`--from` можно указать несколько раз — журналы объединяются, например из разных джоб CI или окружений. В
JSON у каждого роута появляется `executed` (и `via`), у каждого кода ответа — `seen`: приходил ли он на
самом деле. `--min-executed <N>` падает, если выполнено меньше `N` процентов роутов, а `--uncovered`
показывает и невыполненные роуты.

## Параметры

```sh
outry coverage [DIR] [--min <N>] [--from <FILE>]... [--min-executed <N>] [--uncovered]
               [--format text|github|json]
```

`DIR` — сервис на Go или Rust. По умолчанию — папка с `go.mod` или `Cargo.toml`, которая ищется от проекта
вверх до корня репозитория.

| Флаг | Описание |
|------|----------|
| `--min <N>` | Код выхода `1`, если проверено меньше `N` процентов роутов |
| `--from <FILE>` | Журнал `outry run --coverage-out`: отметить выполненные роуты; можно несколько раз |
| `--min-executed <N>` | Код выхода `1`, если выполнено меньше `N` процентов роутов (нужен `--from`) |
| `--uncovered` | Показать только дыры: роуты без запроса, без `expect`, с непроверенными кодами ответа или (с `--from`) невыполненные |
| `--format <F>` | `text` (по умолчанию), `github` (аннотации GitHub Actions), `json` |
| `--json` | То же, что `--format json` |
| `--base <NAME>` | Переменная с адресом сервиса в URL `.http` (для сопоставления), по умолчанию `base` |
| `--query <FILE.scm>` | Дополнительный запрос tree-sitter для другого роутера; можно несколько раз |
| `--project <DIR>` | Папка проекта с `env.toml` |

`outry check` печатает строку итога покрытия, если нашёл `go.mod` или `Cargo.toml`. Низкое покрытие там не ошибка; порог
задаёт `outry coverage --min`.

## В CI

```yaml title=".github/workflows/api-tests.yml"
- name: Route coverage
  run: outry coverage --min 80 --format github
```

Чтобы требовать ещё и того, что роуты реально выполнялись, запишите журнал в шаге с тестами и передайте
его дальше:

```yaml title=".github/workflows/api-tests.yml"
- name: API tests
  run: outry run api --env ci --coverage-out run.json
- name: Route coverage
  if: always()
  run: outry coverage --from run.json --min 80 --min-executed 90 --format github
```

С `--format github` каждая дыра — предупреждение прямо в пулл-реквесте: роут без запроса отмечается на
регистрации в коде, запрос без `expect` — на самом запросе, непроверенный код ответа — на строке обработчика,
которая его отдаёт, а с `--from` невыполненный роут — на его запросе. Ниже порога джоба падает с аннотацией-ошибкой.

`--format json` печатает итоги (`percent`, `checked`, `requested`, `total`, `statuses_checked`,
`statuses_total`, `passed`, а с `--from` ещё `executed`, `executed_percent`) и каждый роут с уровнем, запросами и кодами ответа.

## В приложении

Вкладка **Routes** показывает то же покрытие: строку итога под планом, бейдж у каждого роута с запросом
(`no expect`, `unchecked 404`, `checked`) и **Show N gaps only**, чтобы скрыть полностью проверенные роуты.
Роуты без запроса — в списке **New**, их создаёт **Create files**.
